## 零、操作系统平台支持状态（与本文客户端矩阵正交）

本文其余章节讨论的是「MCP 客户端」兼容性。操作系统层面另有一张独立口径表，避免把「客户端支持」误读成「平台已验证」：

| 平台 | 状态 | 验证程度 |
|---|---|---|
| **Windows 10 / 11（x64）** | ✅ **主打平台，已真机验证** | 本组实验 20 次连续请求真机端到端（真实客户端挂载 + 厂商 usage 回读）、便携包解压即跑、95 项测试全通、日志实测 `%LOCALAPPDATA%\DoboCache\logs` |
| **Linux（x86_64）** | 🟡 **容器环境已实测（非桌面真机）** | 2026-11-04 在 Docker `linux/amd64` + Node 官方 Linux 镜像内对**本发布包自身**做真实运行：解压即跑、`initialize`/`tools/list` 返回合法、9 个工具全在、`cf_judge` 命中、`cf_inject` 返回 `prefixReady=true`、日志按 `~/.local/state/dobocache` 落盘并可读、`XDG_STATE_HOME` 生效、`DOBOCACHE_LOG_DIR` 优先级最高、只读目录降级不崩溃、Node 16 启动自检 `exit 1`。详见本文「附录 A」。**桌面 Linux 真机 + 图形客户端挂载、arm64 架构仍未验证** |
| **macOS（Apple Silicon / Intel）** | 🟡 **CI 真机冒烟已通过** | 真实 Mac 机器上跑通 `npm ci` → `tsc` → `tsc --noEmit` → `eslint` → `vitest` → 首屏命令冒烟 → MCP stdio 握手（9 工具齐全）→ 日志目录断言；Apple Silicon（`macos-latest`）与 Intel（`macos-13`）两架构均在 CI 矩阵内。**未做**桌面客户端长会话实测 |

口径约定：

1. 「支持某客户端」只指该客户端的 stdio MCP 挂载配置方式成立（见 §一 的 7 家取证清单），不代表该客户端在 Linux / macOS 上被真机验证过；
2. 便携包不含原生二进制（`.node` / `.exe` / `.dll` 为 0），故不存在 ABI 兼容问题，但**不等于平台已验证**；
3. Linux / macOS 的问题反馈请按 `README.zh.md`「平台支持状态」一节的渠道与信息清单提交（`node -v` / `uname -a` 或 `sw_vers` / `cf_report` 的 `logDir` + `logDirSource` / 报错原文）；
4. 把 macOS / Linux 从「未验证」推进到「可自动验证」的路径（持续集成配置）见本文 **§八**；该流水线现已启用，macOS 与 Linux 每次提交都跑真实进程冒烟，上表状态即按此口径更新（**冒烟通过 ≠ 桌面客户端长会话已验证**）。

## 二、逐客户端细节（配置路径 / 格式）

### 1. Claude Desktop
- **配置**：`claude_desktop_config.json`，JSON，顶层 `mcpServers`；stdio 用 `command` / `args` / `env`。
  - macOS `~/Library/Application Support/Claude/claude_desktop_config.json`
  - Windows `%APPDATA%\Claude\claude_desktop_config.json`
  - Linux `~/.config/Claude/claude_desktop_config.json`
  - 入口：Settings → Developer → Edit Config（文件不存在时自动创建）
- **自定义端点**：官方配置文档只涉 `mcpServers`，未见 `base_url` / 兼容 provider 配置项 → `未确认`（不宜宣称支持）。
- **缓存字段可见性**：官方文档未说明界面或日志会展示 provider 返回的 usage（含 cache 字段）→ `未确认`。
- 来源：https://modelcontextprotocol.io/docs/develop/connect-local-servers

### 2. Cursor
- **配置**：JSON，`mcpServers`；stdio 用 `command`/`args`/`env`，远程用 `url`/`headers`。项目级 `.cursor/mcp.json`，全局 `~/.cursor/mcp.json`；支持 `${env:NAME}`、`${userHome}`、`${workspaceFolder}` 等插值。
- **自定义端点**：支持"自带 Key"（Settings → Models，可粘贴 OpenAI / Anthropic / Google / Azure OpenAI / AWS Bedrock 的 Key；自带 Key 仅作用于 chat 模型，Tab 补全仍用内置模型）。文档只给出上述厂商的 Key 输入框，**没有自定义 `base_url` 字段** → 无法把请求指向第三方 OpenAI 兼容端点。
- 来源：https://cursor.com/docs/mcp ；https://cursor.com/help/models-and-usage/api-keys ；https://cursor.com/docs/models-and-pricing

### 3. Cline
- **配置**：JSON，`mcpServers`；stdio 支持 `command`/`args`/`env`，另有 `disabled`、`autoApprove`、`type`；同时支持远程 HTTP / SSE。CLI 路径 `~/.cline/data/settings/cline_mcp_settings.json`（可用 `CLINE_MCP_SETTINGS_PATH` 覆盖）；IDE 扩展在 MCP Servers 面板点 Configure MCP Servers 编辑同一 JSON。
- **自定义端点**：支持 "OpenAI Compatible"，需填 `Base URL`、`API Key`、`Model ID`。
- 来源：Cline 官方文档 MCP 配置页（https://docs.cline.bot ）；https://github.com/cline/cline/blob/main/docs/provider-config/openai-compatible.mdx

### 4. Continue
- **配置**：两种——(a) `.continue/mcpServers/` 目录下 YAML（`type` 支持 `stdio` / `sse` / `streamable-http`）；(b) 直接复用 Claude / Cursor / Cline 的 JSON 配置（自动识别）。**MCP 仅在 agent 模式生效**。
- **自定义端点**：`config.yaml` 的 models 支持 `provider: openai` + `apiBase` + `apiKey`。
- 来源：https://docs.continue.dev/customize/deep-dives/mcp ；https://docs.continue.dev/reference

### 5. Codex CLI
- **配置**：TOML，`$CODEX_HOME/config.toml`（默认 `~/.codex/config.toml`）；`[mcp_servers.<name>]` 配置 stdio（`command` / `args` / `env`）。
- **自定义端点**：`[model_providers.<id>]` 支持 `base_url`、`env_key`、`wire_api`（`"chat"` 或 `"responses"`，默认 `"chat"`）。
- **缓存字段**：遥测（OTel）事件含 `cached_token_count`（文档注明 **responses only**、可选），需开启遥测。这是 8 家中唯一在文档里写明 cache token 字段名的客户端。
- 来源：https://github.com/openai/codex/blob/main/docs/config.md

### 6. Gemini CLI
- **配置**：JSON，`mcpServers`（stdio 用 `command`，远程用 `url` / `httpUrl`）。用户级 `~/.gemini/settings.json`；项目级 `.gemini/settings.json`；另有系统级 settings.json。
- **自定义端点**：官方文档未见 `base_url` 或 OpenAI 兼容 provider 配置项，provider 体系为 Gemini API Key / Vertex AI → `未确认`。
- **缓存字段**：`/stats` 可看 cached tokens，**仅 API Key / Vertex AI**，OAuth 登录不支持缓存。
- 来源：https://geminicli.com/docs/reference/configuration/ ；https://geminicli.com/docs/cli/token-caching/ ；https://geminicli.com/docs/cli/generation-settings/

### 7. Cherry Studio
- **配置**：界面配置（非文件）：【设置】→【MCP】→【MCP 服务器】→【添加】；本地服务器填命令 / 参数 / 环境变量（即 stdio），远程填 SSE 或 Streamable HTTP。官方文档未给出配置文件落盘路径 → 路径 `未确认`。
- **自定义端点**：支持"自定义服务商"（设置 → 模型服务 → 添加服务商），填名称、API 密钥、端点设置，"更多设置"可再加 OpenAI Responses、Gemini 等 Base URL。
- 来源：https://docs.cherryai.com.cn/advanced-basic/extensions/mcp ；https://docs.cherryai.com.cn/pre-basic/providers/zi-ding-yi-fu-wu-shang ；https://docs.cherryai.com.cn/pre-basic/providers

### 8. Trae
- **配置**：JSON，`mcpServers`；stdio 用 `command`/`args`/`env`，HTTP 用 `url`/`headers`；超时可用 `START_MCP_TIMEOUT_MS` / `RUN_MCP_TIMEOUT_MS`；变量仅支持 `${workspaceFolder}`；命令字符串中不能含空格。全局在 设置 → MCP → 添加 → 手动添加（粘贴 JSON）；项目级 `项目根/.trae/mcp.json`（需先在设置中开启"项目级 MCP"）。
- **自定义端点**：支持"自定义模型"，可选 API 格式（OpenAI Chat Completions / Anthropic Messages）、自定义请求地址、模型 ID、API 密钥。
- 来源：https://docs.trae.cn/ide_add-mcp-servers ；https://docs.trae.cn/ide_custom-models ；https://docs.trae.cn/ide_model-context-protocol

### 9. Windsurf（未确认，不纳入结论）
调研时 `docs.windsurf.com` 连接被拒，`windsurf.com/docs`、`codeium.com/docs/windsurf/mcp` 均超时，四项均无法取证 → 全部 `未确认`，**暂不列入支持清单**，待官方文档可访问后补齐。

## 五、复现验证方法（可直接用作"如何验证"章节）

对支持 `base_url` 的 5 家客户端，按以下步骤确认"请求确实经过 DoboCache 且缓存生效"：

1. 按 §二 配置 MCP server 指向 `<解压目录>/dist/index.js`，并在模型侧把端点指向待测的 OpenAI 兼容地址；
2. 发送同一个固定 prompt 两次（第二次请求前缀完全相同）；
3. 在 DoboCache 侧日志（v0.4.4 起默认 `<平台标准日志目录>/dobocache-<日期>.log.jsonl`：Windows `%LOCALAPPDATA%\DoboCache\logs`、macOS `~/Library/Logs/DoboCache`、Linux `$XDG_STATE_HOME/dobocache`，可用 `DOBOCACHE_LOG_DIR` 覆盖；实际目录以 `cf_report` 返回的 `logDir` 为准）确认出现对应记录，且 `prefixReady=true`；
4. 比对**第二次**请求的厂商 usage 缓存字段是否大于 0；
5. Codex CLI 可额外设 `wire_api = "responses"` 并开启遥测，核对 `cached_token_count`。

Cursor / Claude Desktop / Gemini CLI 仅声明"MCP 挂载可用"，**不作为缓存字段可观测的示例**。

## 八、后续三平台自动验证路径（持续集成）

### 八.1 这一节解决什么问题

当前平台状态是：Windows 已真机验证、Linux 仅容器内实测、macOS 已由 CI 在真实 Mac 上跑通冒烟链路（桌面客户端长会话仍未实测）。人肉找机器验证成本高且不可重复。本仓库已内置一套 **GitHub Actions 三平台流水线**，把「Windows / Linux / macOS 各有一次真实进程验证」变成每次提交自动执行，只需把源码推到 GitHub 即可启用。

### 八.2 仓库内已就位的两个文件（均不进入对外发布 zip 包）

| 文件 | 作用 |

### A.5 容器环境下的已知观察（非缺陷）

1. **不可写场景的 errno 取决于构造方式**：只读 bind mount 上 `mkdir` 返回 `ENOENT`、`writeFile` 返回 `EROFS`；以非 root 用户访问 `chmod a-w` 目录则返回 `EACCES`。因此降级提示里的括号内容会随构造方式变化（`ENOENT` / `EROFS` / `EACCES`），属内核与挂载实现特性；降级行为本身（不写日志、不崩溃、缓存功能不受影响）与设计一致。
2. **`logFile` 字段在 `disabled` 状态下仍会给出候选路径**：该字段在降级时仅供展示"最后尝试的路径"，实际未写入文件；判断是否真正落盘请看 `logDirSource` 是否为 `disabled`。

**A.8.1 入口转发（P0 回归）**

v0.5.1 的问题：包里有两个 `bin`（`dobocache` 与 `dobostitch`），`npx dobocache@0.5.1 dobostitch start` 只会跑与包同名的那个，`dobostitch` 被当成普通参数传进去，而入口当时不读 `argv`，于是起了一个 stdio MCP server 并因等不到输入挂住。v0.5.2 让入口读参数：

```bash
node dist/index.js dobostitch status
```

实测输出（原文，节选首行）：

```
[dobostitch] 最近会话（共 43 个，目录 C:\Users\Administrator\AppData\Local\DoboCache\handoff）：
```

即 `argv[2] === "dobostitch"` 时参数被原样交给代理 CLI，代理命令正常执行、不再起 MCP server。同时 `npx -p dobocache@0.5.2 dobostitch start` 这条显式路径仍然可用，原 `dobostitch` bin 行为不受影响。

printf '%s\n' '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"manual","version":"1"}}}' \
