# 我以为是"缓存没生效"，其实是缓存每次都被我自己的请求打碎了

> **仓库**：https://github.com/dobo123123/dobocache　｜　**本版安装包 v0.4.9**：https://github.com/dobo123123/dobocache/releases/tag/v0.4.9　｜　**复现材料与文档**：https://github.com/dobo123123/dobocache/tree/main/release

> 一个给编码 CLI / Agent 客户端用的本地 MCP 小工具：把上下文整理成稳定前缀，并把每一步调整写进本地白盒日志。开源，纯本地，不联网。
> 文末有 20 次连续请求的对照数据和完整复现材料，欢迎来打我脸。

---

## 一、起因：一个"看起来在省，其实一分没省"的误判

各家厂商 API 都有 prompt caching：请求开头如果和上一次逐字节相同，这部分就按缓存计费，不再全量重算。听起来很省。

但我连续几天观察自己的编码 CLI 用量时发现一件事：**我的请求明明"看起来"几乎一模一样，缓存命中却时有时无，甚至整段对话一次都没命中。**

排查下来，问题不在厂商，在我自己的请求：

1. 拼接顺序在两次请求之间变了（system prompt 的位置、工具描述的顺序）；
2. 历史裁剪之后，前缀尾部落在缓存块边界中间（常见 128 token 分块），尾部半块命中不了；
3. **前缀比厂商的最小可缓存长度还短**，根本进不了缓存；
4. 重复指令和重复文档块让前缀越长越脏。

这四条里任意一条成立，整段前缀的缓存就**全部作废**——你以为在用缓存，其实每次都在全量重算。

DoboCache 干的就是把这几处"差一点点"补齐，并且**把每步改了什么、为什么改，写进本地日志**。

## 二、它具体做什么

三个核心动作，全部记录在案：

| 动作 | 解决什么 |
|---|---|
| 去重（`dedup`） | 折叠重复指令 / 重复内容，让前缀更干净 |
| 128 token 对齐（`align128`） | 让前缀尾部落在缓存块边界上，减少"差半个块"的部分命中丢失 |
| 过门槛补充（`topup`） | 前缀短于厂商门槛时补至高价值片段，保证能进缓存 |

除此之外还有 `cf_report`（累计统计）、`cf_meter`（用量快照）、`cf_normalize`（内容归一化，返回无内容指纹）。

挂载方式是 **stdio MCP**，在客户端配置里指一下 `dist/index.js` 就行。

## 三、20 次连续请求的对照数据

一套 20 次递进式连续话题（AI 资讯盘点，每次基于前文继续追问，历史逐次累积）；请求端是「某常见编码 CLI 工具」接入（模型来自厂商 G），白盒引擎以 stdio MCP 挂载 DoboCache。同一台机器、同一模型、同一参数，**唯一差别是挂没挂 DoboCache**：

| 指标 | 对照组（不挂） | 实验组（挂） |
|---|---|---|
| 20 次请求的平均命中率 | **0.00%**（20 次全 0） | **98.59%** |
| 区间 | — | **96.08% – 99.79%** |
| 零命中请求数 | 20 / 20 | **0 / 20** |
| 前缀就绪 | — | **20 / 20** |

然后是我最想强调的一点：**对照组 20 次全 0，不是我挑的数据，而是我每次都在对照组请求头部注入了不同的随机噪音**，故意让前缀漂移。

这恰好说明了一件反直觉的事：**前缀只要变一点，厂商侧的缓存就整段失效**。所以"我感觉我的请求差不多啊"这个感觉，一文不值。

反过来说：如果对照组不做噪音注入，它会自然命中相当一部分输入，这时候你对比的根本不是"有没有这个工具"，而是"厂商缓存窗口当时什么状态"。**这也是我这套实验最容易做错的一步**，谁要复现，务必注意。

这不是理论担心。我拿三种请求端形态各跑了 20 次，同一条挂载逻辑（下文用代号：**WBX** 我自己写的白盒直连底座、**DXH** 官方 Harness headless、**COD-X** 常见编码 CLI；代号只是类型缩写，不点具体产品名）：

| 请求端形态 | 版本（对应实验） | 不挂（对照组） | 挂（实验组） |
|---|---|---|---|
| WBX 白盒引擎直连 | v0.4.0（031）/ v0.4.2（032） | 0.00% / 0.00% | 93.09% / 91.89% |
| DXH 官方 Harness headless | v0.4.0（033）/ v0.4.2（034） | 66.00% / 68.09% | 96.85% / 95.91% |
| COD-X 常见编码 CLI | v0.4.2 候选（组 7）/ v0.4.3（组 8） | 9.87% / 0.00% | 90.58% / 98.59% |

"WBX 白盒引擎直连"那两行对照组是 0%，原因得说清楚：**那套请求端是我自己写的白盒测试底座**（不是任何官方客户端），**故意什么前缀处理都没做**——不构造前缀、不预热缓存、不复用会话，每轮只发「任务原文 + 随机噪音」。请求端手里压根没有可复用的前缀，命中当然是 0，这是**结构性零基线**，不是"厂商缓存被打崩"。

「官方 Harness」那种请求端每次新会话自带约 2,560 tokens 的厂商全局系统前缀缓存，什么都不做对照组就有 66%–68%（实验 033 累计命中 51,200 tokens，正好 2,560 × 20，自己一除就知道这份 66% 全是官方前缀垫的，跟我这插件没关系）。但别急着羡慕：在 v0.4.0 那批里它随请求噪音累积从 84.27% 一路劣化到 54.54%，缓存照样脆，只是起点高。

所以准确的说法是：**不挂载约 0%–68%（看请求端形态），挂载后 90%–98%**。跨形态的对照值不能互比，能比的只有同一形态里的"挂 vs 不挂"。

（口径补一句：A/B 两栏是 20 次的累计口径，C 两栏是 20 次逐次命中率的均值，两种算法不同，跨形态只看量级。表里每个数都能在随包 `testdata/hitrate-multi-platform-summary-20261105.csv` 里找到对应行——A/B 的分子分母就在同一行的 token 列，C 的逐次值在同目录逐次 CSV，自己除一遍就知道我没挑数。）


还有 COD-X 那两格（9.87% 和 0.00%）我得单独交代一句，不然特别容易被读成"这工具把命中从 0 拉到 98"。两轮是同一形态、同一套 20 次任务、同样的对照组做法（每次在头部塞不同的随机噪音），只有挂的版本不同——对照组压根不挂插件，跟版本没关系，所以这两个数的差别不是我越做越差，是噪音的随机性：组 7 的 R10、R20 那两次，历史已经堆到 10 轮 / 19 轮，长前缀够长，厂商缓存自己对上了，读到 **99.27% / 98.10%**；组 8 那 20 次全被打散，次次 0。

说白了，这组数恰恰证明厂商自带缓存本身很能打——**只要前缀稳，它就能吃满接近 99%**，卡点从头到尾只有"前缀稳不稳"这一件事。我做的是把前缀稳住，不是凭空造命中。所以别拿这两格去推"提升 98 个点"，那是我自己设的压力条件，不是谁的日常。

顺带交代组 7 实验组均值 90.58% 为什么比组 8 低 8 个点：R9、R13、R16 撞上厂商侧抖动（53.08% / 85.53% / 0%），把这 3 次剔掉，其余 17 次均值 **98.41%**，跟组 8 按同一位置剔除后的 98.57% 只差 0.16pp——两个版本在稳定段上是一样的，不是"升级涨了 8 个点"。

另外必须说清楚：**命中率是单次请求自己输入内部的缓存占比，不是省了多少 token 的绝对数**。两组输入量本来就不同（对照组输入随请求次数从 39 涨到 2738 tokens，实验组稳定在"前缀 + 尾部"），不能跨组换算，也不能和别的实验混比。

还有一句得主动交代：**我们测的都是"短请求"**。8 组对照、每组 20 次连续请求，单轮输入就是几百到几千 tokens 的资讯盘点，**没有测单轮上万 tokens 的长文档、整库代码分析、几十轮超长会话这类长任务**。缓存前缀复用在这个体量上成不成立，我没测过，就不替它说好话。

你要是手上正好有这种长任务，欢迎挂上去跑一遍，把逐次 usage 记下来发我——这比我在帖子里吹任何数字都有用。逐次数据、任务原文、复跑步骤我都塞进包里了，本来就指望别人来验我。

## 四、白盒日志长什么样

每次 `cf_inject` 都会落一条 JSONL。下面是按 **v0.4.6 口径**输出的一条示例（脱敏字段照旧，`reqIndex` 是请求序号，`hitRate` 拿不到厂商 usage 时写 `null`）：

```json
{
  "requestId": "req-1b0ff98f",
  "ts": 1793709231484,
  "reqIndex": 2,
  "promptChars": 36,
  "rawTokens": 201,
  "optimizedTokens": 4096,
  "changes": [
    {"kind": "align128", "detail": "追加 98 个对齐块"},
    {"kind": "topup",    "detail": "补充 63 块（高价值片段/文档块）"},
    {"kind": "scenario", "detail": "首条请求或缓存为空：轻量约束放行自由回答"}
  ],
  "note": "cf_inject：原始 201 tokens → 优化后 4096 tokens（前缀 4096 + tail）；实际门槛 3450 tokens。",
  "sessionId": "sid-b6ca1662",
  "prefixTokens": 4096
}
```

我认为这比"命中率 98%"这个数字有用得多：出问题时你能看见是哪一步没做、门槛多少、补充了多少块。

## 五、v0.4.4 → v0.4.7 做了什么（以及没做什么）

**只做隐私，不动命中逻辑。**

这个版本之前，日志的 `requestId` 字段存的是**用户提问原文**——日志是本地的、不外传，但存在本地就是风险。v0.4.4 改成：

- `requestId` → `req-<8 位 hash>`（同文恒定、不可反推）
- `sessionId` → `sid-<8 位 hash>`
- 新增两个纯数字字段 `round`（请求序号）/ `promptChars`，保住"第几次请求""是不是同一提问"的对照能力
- 写盘走字段白名单，之后新增字段即使带正文也写不进去

对照 5 次真实冒烟：`cf_judge` / `cf_inject` 输出与上一版**逐字节一致**，`prefixHash` 恒定，命中相关代码 MD5 未变，94 个测试全绿。

### v0.4.6：把"看不见的成本"和"读错的数字"一起修掉

发布前被一位同行指出两个问题，都不是功能 bug，但都该修：

**一、白盒报告卡片默认关了。** 报告本身是给人看的，但它写进对话上下文就**占 token**——每次工具调用带一张，一张约 300+ tokens，长会话里累积起来比想象中贵。v0.4.6 起默认 `quiet`：只写本地日志、不随工具返回。要看累计数据调 `cf_report`（读本机日志，不花 token）；要看单次详情设 `DOBOCACHE_WHITEBOX=once`（出一次后自动回落）或 `always`（每次都要，代价就是那 300+ tokens/次）。首次运行会给一条一次性提示，之后不再打扰。

**二、命中率不再写 0 假装有数。** 原来 `cf_judge` / `cf_inject` 在请求发出前落日志，此时拿不到厂商 usage，就写了 `hitRate: 0`。问题是这样会被读成"命中率 0%"——和同包 CSV 里来自厂商 usage 的 98.59% 放在一起看，就成了自相矛盾。v0.4.6 改成：拿不到厂商 usage 就写 `null`（未判定），要做真实命中率就把 `hitTokens` / `missTokens` 传进来。

**三、术语"轮"彻底废掉。** "轮"在我们的语境里指什么——一次 LLM 请求？一个用户回合？一次工具调用？说不清。日志里的 `round` 其实一直是"本机进程内第几次请求"，跟对话阶段无关，这个字段名容易误读。v0.4.6 起日志字段更名 `reqIndex`，文档里统一说"第几次请求"，不再出现"轮"。

**四、随包证据只提供 CSV。** 包内证据是 CSV（数字取自厂商 `usage`）+ 任务清单 + 回归报告，不附 JSONL 日志；报告的每一个数字都能在这三份材料里逐项核对。

**没有宣称任何性能提升**——这个版本命中率与上一版一致，别期待数字变高。

### v0.4.7：给日志加上边界，让累计数据活得比进程长

也是两个不是功能 bug、但长期挂着就会咬人的问题：

**一、日志只增不减。** 挂在客户端里天天跑，日志文件只长不缩，最后无声吃掉磁盘。v0.4.7 起自动维护：单文件超 10 MB 滚成 `.1`、最多留 3 份副本、超过 7 天的清掉；而且**只碰自己命名的 `dobocache-*.log.jsonl`**，同目录下别的文件一律不动。当前生效策略可以用 `cf_report` 的 `logPolicy` 查，真执行过清理时 `logMaintenance` 会告诉你删了几个、释放多少字节。上限和保留天数分别用 `DOBOCACHE_LOG_MAX_MB` / `DOBOCACHE_LOG_KEEP_DAYS` 调。

**二、累计数据一重启就归零。** 以前 `cf_report` 只读当前进程内存，MCP 客户端重启一次，前面的统计全没了——看到 0 很容易误判成"白盒根本没工作"。现在传 `source="disk"` 会从本地日志重新聚合，`days` 指定回看几天（默认等于日志保留天数）。口径与内存态严格一致，不新造指标：`hitRate` 只对能判定的行求均值，一行都判不出来还是 `null`，不会伪造 0%。

另外澄清一处名字误导：`cf_prune` 听起来像"清理日志"，其实**只修剪你传进去的文本**，不读、不删磁盘上任何文件。行为一直是那样，本版只是把描述写清楚了。

**缓存核心依然零改动**——前缀冻结、对齐、分级准入、判定逻辑与 v0.4.4 / v0.4.6 一致，本版只动"日志的生命周期"和"累计数据的读法"，命中率数字不会因为升级变高。

顺带说：旧版本产生的历史日志里 `requestId` 还是原文，升级不会追溯修改，需要自己清理。

## 六、能挂在哪些客户端

只写有官方文档支撑的，其余标"未确认"：

- **stdio MCP 挂载**：Claude Desktop、Cursor、Cline、Continue、Codex CLI、Gemini CLI、Cherry Studio、Trae 官方文档均有说明（Windsurf 文档站当天打不开，不列入）。
- **能把请求指向自定义 OpenAI 兼容端点**：Cline、Continue、Codex CLI、Cherry Studio、Trae 五家；**Cursor 不行**（只能填官方厂商 Key，没有 base_url 字段）；Claude Desktop 与 Gemini CLI 文档中未见兼容端点入口。
- **客户端里能不能直接看到缓存命中**：目前只有 Codex CLI（遥测字段 `cached_token_count`，仅 responses）和 Gemini CLI（`/stats`）有文档证据，而且都不是"面板直接显示"。所以准确的表述是：**DoboCache 在服务端读取厂商 API 的 usage 缓存字段并记录、回传**，客户端侧可视化要逐个实测。

不想在这一点上吹，因为吹了第一个来问的人就能戳破。

## 七、自己复现要准备什么

材料都在仓库 `release/` 下：

- 20 次请求的任务原文（一字未改，跨版本可比的前提）
- 逐次 CSV（列名 `round` 是历史命名，语义即"第几次请求"；`raw_tokens, opt_tokens, hit_rate, saved_tokens` 同前）
- ~~白盒日志（脱敏版）~~ → **v0.4.6 起不随公开包分发**（旧口径 `hitRate` 恒 0，易与 CSV 同名字段混读），改由 CSV 提供逐次数据
- 回归报告（含门槛证据、20 次全表、判读标准逐条对照）
- 复跑说明（含 5 条常见坑）

复跑要做对的三件事：

1. 实验组 `cf_inject(reset=true, sessionId=<新会话>, minPrefixTokens=<厂商门槛>)`；门槛不够高就传 3000（实际生效 3450）；
2. 每次发两遍相同请求，**取第二遍**的 usage；
3. 对照组**每次头部注入不同随机噪音**。

验收：日志里 `prefixReady=true`、`effectiveMinPrefixTokens` 等于配置门槛 × 1.15、实验组第二次请求起稳定 90%+。

## 八、它不适合谁

- 只跑一两次请求的：第一次请求必然在建缓存，没有命中，别指望；
- 上下文本来就短、低于厂商最小缓存长度的：省不出东西；
- 客户端不支持自定义端点的（如 Cursor）：请求过不去，挂 MCP 也没用；
- 想要"一键看见省了多少钱"的：本项目对外**不报金额**，只给命中率和相对比例——不同厂商计费规则差异太大，跨组换算的结论基本都是错的。

## 九、最后

这个工具解决的不是"缓存技术有多难"，而是"**你根本不知道自己的缓存有没有生效**"。白盒日志就是为了解决后者的。

欢迎拿自己的场景复现，尤其是反对意见：如果你的对照组在不加噪音的情况下也大量命中，或者你测出的前缀稳定性比这个差得多，那都是很有价值的补充。

材料在仓库 `release/`，复现步骤、原始数据、坑位说明都在里面。
